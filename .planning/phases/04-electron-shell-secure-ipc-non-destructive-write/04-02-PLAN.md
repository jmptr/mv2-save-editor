<objective>
Build the pure IPC boundary module `src/ipc/ipc-guards.ts` — the defense-in-depth SHAPE guard and
the offset-stripping/int64-string bridge that sit between the untrusted renderer payload and the
trusted core. The core (`patchSave`) already owns all range/kind/readOnly validation; this module
owns exactly two boundary concerns: (1) reject a malformed `edits` payload BEFORE it touches the
core (SC-4), and (2) enforce the wire contract — offsets never cross the bridge and int64 crosses
as strings (SC-4 / D-04).

Purpose: the trust boundary. Every `preview`/`write` IPC call funnels through these functions, so a
malformed payload or an offset leak is caught here, in a unit-tested pure module, not in the thin
electron wiring. Supports IO-02 (the write path resolves edits through `toEdits`).
Output: `src/ipc/ipc-guards.ts` + two test files.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer → main IPC payload | Untrusted `edits` array crosses into the trusted core here. |
| main → renderer change report | Internal ChangeReportRow (carries byte offsets) must be sanitized before it leaves main. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-4-02 | Tampering | assertEditsPayload (IPC edits payload) | high | mitigate | Hand-rolled SHAPE guard rejects non-array / non-object / bad key / non-finite number / non-integer int64 string with IpcArgError before the core runs; the core (`patchSave`) re-validates ranges/kind/readOnly (defense in depth, SC-4). |
| T-4-03 | Information Disclosure | toWireReport (change report) | high | mitigate | The IPC-facing WireChangeRow type omits `offset`; toWireReport drops it and the wire-shape test asserts via `assertNoOffsets` that no offset key crosses at any depth (SC-4). |
| T-4-08 | Information Disclosure | int64 currency serialization | medium | mitigate | int64 crosses as a decimal string both directions (never a JSON number → no precision loss past 2^53; never a raw bigint → serializable). |
</threat_model>
