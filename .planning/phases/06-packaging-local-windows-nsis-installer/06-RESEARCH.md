# Phase 6: Packaging — Local Windows NSIS Installer - Research

**Researched:** 2026-07-09
**Domain:** Electron desktop packaging — electron-builder 26.x + NSIS per-user installer, Windows `.ico`, cross-platform build reality
**Confidence:** HIGH (config shape, defaults, cross-platform constraint verified); MEDIUM (a few NSIS default values documented from search, not direct-fetched — docs site 403s the fetcher)

## Summary

This phase adds a **package step only**: an `electron-builder` dev-dependency, a config block, an `npm run package` script, a committed placeholder `build/icon.ico`, a version bump to `1.1.0`, and distribution metadata (`appId`, `productName`). It does **not** touch `electron/main.ts` logic, `scripts/build.mjs`, or the parser/writer core. electron-builder consumes the esbuild `dist/` as-is and never recompiles TypeScript.

The single largest planning risk is **cross-platform build reality**: this repo's dev host is **Linux** (`node_modules` currently has no `electron` installed either), and electron-builder must run **Wine** on Linux/macOS to (a) run `rcedit.exe` to stamp the `.ico` + version metadata into the app `.exe`, and (b) run `makensis` to produce the NSIS `Setup.exe` [VERIFIED: electron-userland/electron-builder + electron/windows-installer docs]. Without Wine, producing the actual `release/MV2 Save Editor Setup 1.1.0.exe` fails on this host. Therefore PKG-01 (produce the `.exe`) and PKG-02 (installed app runs the loop) are **manual, Windows-only acceptance gates** — analogous to v1.0's mandatory in-game load check — while everything else (config correctness, version, appId/productName/artifactName, `.ico` validity, asar sibling layout) is **assertable cross-platform**. This split feeds the Validation Architecture section directly and aligns with the already-planned Phase 8 `windows-latest` CI runner.

Two config facts drive almost every decision: **`directories.output` defaults to `dist`** (which esbuild owns) so it **must** be overridden to `release/`; and the **default `artifactName` template is `${productName} Setup ${version}.${ext}`**, which with `productName: "MV2 Save Editor"` and version `1.1.0` yields exactly `MV2 Save Editor Setup 1.1.0.exe` with **no custom template needed**.

**Primary recommendation:** Put the electron-builder config in a standalone **`electron-builder.yml`** (idiomatic for keeping a growing build block out of package.json); set `appId`, `productName`, `directories.output: release`, `files: [dist/**, package.json]` (lean asar — esbuild already bundles react/tanstack into `dist/renderer.js`), `win.target: nsis`, `win.icon: build/icon.ico`, and `nsis: { oneClick: true, perMachine: false }` (defaults, but state them explicitly for the acceptance bar). Generate the placeholder `.ico` with a **zero-dependency pure-Node writer** (verified below) rather than adding a flagged npm dep. Chain `package` as `build:electron && electron-builder --config electron-builder.yml`.

### Pattern 1: Standalone `electron-builder.yml` for a lean, in-place-patched app
**What:** Keep the build config in its own file; ship only the esbuild output.
**When to use:** Always here — the renderer deps are already bundled by esbuild, so the asar needs only `dist/**` + `package.json`.
**Example:**
```yaml
# electron-builder.yml   [CITED: electron.build/configuration + electron.build/nsis]
appId: com.jmptr.mv2-save-editor        # D-02 — AppUserModelID, stable across releases
productName: MV2 Save Editor            # D-01 — installer name, shortcut label, install folder
directories:
  output: release                       # OVERRIDE default "dist" (esbuild owns dist) — PKG-04
  buildResources: build                 # default; where build/icon.ico is auto-found
files:
  - dist/**                             # main.js, preload.js, renderer.js, index.html (+maps)
  - package.json                        # required: provides `main: dist/main.js` inside asar
# asar: true is the default — leave on (packs app source into app.asar)
win:
  target: nsis                          # default Windows target
  icon: build/icon.ico                  # PKG-04 — ≥256×256 (rcedit embeds into .exe)
nsis:
  oneClick: true                        # PKG-03 — silent per-user, no wizard, no UAC
  perMachine: false                     # PKG-03 — HKCU/%LOCALAPPDATA%, no admin
  createStartMenuShortcut: true         # PKG-03
  createDesktopShortcut: true           # optional (default true) — planner's call
  # artifactName omitted → default "${productName} Setup ${version}.${ext}"
  #   → "MV2 Save Editor Setup 1.1.0.exe"  (exactly the target name — no template needed)
```

### Pattern 2: Chained `package` script (D-05)
```json
// package.json "scripts"
{
  "package": "npm run build:electron && electron-builder --config electron-builder.yml",
  "package:dir": "npm run build:electron && electron-builder --dir --config electron-builder.yml"
}
```
`package:dir` (`--dir`) produces the unpacked app (`release/win-unpacked/`) without the NSIS installer step — useful for faster iteration and (on Windows/Wine) for asar-content inspection. A bare `electron-builder`-only script for Phase 8 CI reuse is also acceptable per D-05.

### Anti-Patterns to Avoid
- **Leaving `directories.output` at default (`dist`):** electron-builder would write into esbuild's `dist/`, colliding with build output and violating PKG-04. Always set `output: release`.
- **Shipping `node_modules` in the asar:** default electron-builder behavior pulls production `dependencies` (react, react-dom, @tanstack/react-virtual) into the asar — but esbuild already bundles them into `dist/renderer.js`. Restrict `files` to `dist/** + package.json` for a lean asar. `electron` stays external (provided as the runtime host by electron-builder, not shipped in the asar).
- **Renaming/moving `dist/` outputs:** any change that breaks the `preload.js`/`index.html`-beside-`main.js` layout breaks `path.join(__dirname, …)` after asar packing (Phase 4 Pitfall 2). Keep `files: [dist/**]` verbatim.
- **Assuming the `.exe` builds on this Linux host without Wine:** it won't (see Cross-Platform Reality). Don't write a plan whose automated verification tries to produce/run the `.exe` on Linux CI.
- **Adding a custom `artifactName` "to get spaces/version":** unnecessary; the default already produces the exact target filename.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| NSIS installer script (per-user, shortcut, uninstaller) | A hand-written `.nsi` | electron-builder `nsis` options | Builder generates a correct, tested NSIS script from a few flags; hand-rolling reintroduces UAC/registry/uninstall bugs |
| Embedding icon + version into the `.exe` | Manual `rcedit` invocation | electron-builder `win.icon` | Builder runs rcedit (via Wine off-Windows) automatically at the right stage |
| asar packing / file collection | Manual `asar` CLI | electron-builder `files` + `asar: true` | Builder handles asar creation, integrity, and native-module unpacking |
| Installer filename with product + version | Custom naming logic | default `artifactName` template | `${productName} Setup ${version}.${ext}` is exactly the requirement |
| `.ico` container assembly | (borderline) an npm image lib | ~40-line pure-Node writer (verified below) | For a *throwaway placeholder* the writer is trivial, correct, and adds zero deps; a real branded icon later can use any tool |

**Key insight:** electron-builder is a large abstraction whose entire value is turning a handful of declarative options into a correct Windows installer. The only thing worth "hand-rolling" here is the *throwaway* placeholder `.ico`, and only because the alternative is a flagged npm dependency for a file that will be replaced.

## Cross-Platform Reality (TOP PLANNING RISK)

**Can electron-builder produce a Windows NSIS `.exe` from this Linux dev host?** Not without extra setup.

- electron-builder runs **`rcedit.exe` via Wine** on Linux/macOS to stamp the icon + version + AppUserModelID into the app `.exe`, and **`makensis` (via Wine)** to compile the NSIS installer. [VERIFIED: electron-userland/electron-builder issues #1062/#2510/#3562 + electron/windows-installer troubleshooting docs] Wine is **required** to build Windows targets off-Windows. [CITED: electron.build/multi-platform-build]
- The default NSIS target does **not** require Mono (Mono is only for Squirrel.Windows). [CITED: multi-platform-build]
- This repo's `node_modules` currently has **no `electron`** installed and there is **no Wine** on the host [VERIFIED: `ls node_modules/.bin` empty of electron; `which wine` absent this session]. So a naive `npm run package` on this host fails at the rcedit/makensis stage.
- electron-builder also **downloads prebuilt binaries** (`app-builder-bin`, NSIS resources, winCodeSign) on first build. `api.npmjs.org` was policy-blocked this session; a sandboxed/offline CI may need these cached.

**Implication for verification:**
- **Windows (or Wine-provisioned) only:** actually producing `release/MV2 Save Editor Setup 1.1.0.exe` (PKG-01) and running the installed app through the full loop (PKG-02, PKG-03 install behavior) — this is the **manual acceptance gate**, the packaging analogue of v1.0's mandatory in-game load.
- **Any OS (Linux dev host / CI):** config schema validity, version bump, `appId`/`productName`/`artifactName` correctness, `.ico` existence + ≥256×256, and `dist/` sibling layout — all statically assertable.
- The project **already plans a Phase 8 `windows-latest` CI runner**; that runner (native Windows, no Wine) is the natural home for the reproducible `.exe` build. For Phase 6, either (a) the developer runs `npm run package` on their own Windows machine (they run Windows per PROJECT.md) and performs the manual loop check, or (b) the plan explicitly defers the artifact-producing verification to the Windows environment and keeps Phase 6's automated gate to config/layout assertions. **Recommend making this split explicit in the plan** so the phase is not blocked on Wine.

## Common Pitfalls

### Pitfall 1: `directories.output` collides with esbuild's `dist/`
**What goes wrong:** electron-builder defaults `output` to `dist`; it writes `win-unpacked/` and the installer into esbuild's directory, mixing/overwriting build output and violating PKG-04.
**Why it happens:** The default is `dist` [CITED: electron.build/configuration]; easy to leave unset.
**How to avoid:** Set `directories.output: release` explicitly. Add `release/` to `.gitignore` (currently absent — the existing bare `dist` ignore does not cover `release/`).
**Warning signs:** New files appearing under `dist/`; `git status` showing installer artifacts.

### Pitfall 2: asar breaks `__dirname` sibling resolution
**What goes wrong:** `main.ts` does `path.join(__dirname, 'preload.js')` / `'index.html'`; if `files` globs or a restructure drop them from beside `main.js`, the packaged app white-screens or fails preload.
**Why it happens:** Over-aggressive `files` filtering, or emitting outputs to different subdirs.
**How to avoid:** `files: [dist/**, package.json]` keeps the three JS files + `index.html` as siblings inside `app.asar`. Inside an asar, `__dirname` + `path.join` resolve correctly (Electron patches fs for asar). Verify by launching the installed app (PKG-02).
**Warning signs:** Blank window, "Unable to load preload", or "index.html not found" only in the packaged build.

### Pitfall 3: `.ico` smaller than 256×256 fails the build
**What goes wrong:** electron-builder errors `image must be at least 256x256`. [VERIFIED: electron-userland/electron-builder issues #2462/#3709]
**Why it happens:** A 32×32 or 48×48 favicon-style `.ico` is below the floor.
**How to avoid:** Ship an `.ico` whose largest entry is ≥256×256. A single 256×256 32bpp entry passes (the writer below does this); multiple sizes (16/32/48/256) are nicer for Windows scaling but not required for a placeholder. [CITED: electron.build/icons.html]
**Warning signs:** Build fails immediately at the Windows target with the 256×256 message.

### Pitfall 4: Trying to build the `.exe` on Linux without Wine
**What goes wrong:** Build fails at the rcedit/makensis stage ("Bad EXE format", wine not found).
**Why it happens:** rcedit + makensis are Windows binaries run through Wine off-Windows.
**How to avoid:** Produce the artifact on Windows (dev machine or Phase 8 `windows-latest`); on the Linux host, limit automated checks to config/layout/asset assertions.
**Warning signs:** `wine`/`rcedit.exe` errors mid-build; passing on Windows CI but failing locally.

### Pitfall 5: node_modules bloating the asar
**What goes wrong:** Default `files` behavior pulls production `dependencies` into the asar even though esbuild bundled them.
**Why it happens:** electron-builder auto-includes prod deps unless `files` is scoped.
**How to avoid:** Explicit `files: [dist/**, package.json]`.
**Warning signs:** Large `app.asar`; `node_modules/react/...` visible in `win-unpacked/resources/app.asar`.

## Code Examples

### Zero-dependency placeholder `.ico` generator (verified this session)
This produces a valid single-entry 256×256 32bpp Windows icon — confirmed by `file`: *"MS Windows icon resource - 1 icon, 256x256, 32 bits/pixel"* [VERIFIED: executed on Node 22 this session]. Run once (`node scripts/make-icon.mjs`), commit `build/icon.ico`, then swap in a real icon later by replacing the one file (no config change — D-03).

```js
// scripts/make-icon.mjs  — throwaway "MV2" placeholder; zero npm deps.
import { writeFileSync, mkdirSync } from 'node:fs';
const SIZE = 256;
const xor = Buffer.alloc(SIZE * SIZE * 4);           // BGRA, bottom-up
for (let y = 0; y < SIZE; y++) for (let x = 0; x < SIZE; x++) {
  const i = (y * SIZE + x) * 4;
  const accent = (x + y) < SIZE;                      // simple two-tone diagonal
  xor[i]     = accent ? 0x2a : 0x1e;                  // B
  xor[i + 1] = accent ? 0x2a : 0x1e;                  // G
  xor[i + 2] = accent ? 0x3c : 0x28;                  // R
  xor[i + 3] = 0xff;                                  // A (opaque)
}
const andMask = Buffer.alloc((SIZE / 8) * SIZE);      // 1bpp mask, all zero (alpha used)
const dib = Buffer.alloc(40);
dib.writeUInt32LE(40, 0);                             // BITMAPINFOHEADER size
dib.writeInt32LE(SIZE, 4);                            // width
dib.writeInt32LE(SIZE * 2, 8);                        // height = 2× (XOR + AND)
dib.writeUInt16LE(1, 12);                             // planes
dib.writeUInt16LE(32, 14);                            // bpp
const image = Buffer.concat([dib, xor, andMask]);
const dir = Buffer.alloc(6);
dir.writeUInt16LE(0, 0); dir.writeUInt16LE(1, 2); dir.writeUInt16LE(1, 4); // reserved, type=icon, count=1
const entry = Buffer.alloc(16);
entry.writeUInt8(0, 0); entry.writeUInt8(0, 1);       // width/height 0 ⇒ 256
entry.writeUInt16LE(1, 4); entry.writeUInt16LE(32, 6);// planes, bpp
entry.writeUInt32LE(image.length, 8);                 // bytesInRes
entry.writeUInt32LE(6 + 16, 12);                      // imageOffset
mkdirSync('build', { recursive: true });
writeFileSync('build/icon.ico', Buffer.concat([dir, entry, image]));
console.log('wrote build/icon.ico', 6 + 16 + image.length, 'bytes');
```

### Optional: set the window icon in main.ts (dev/Linux only)
On the **packaged Windows** app the taskbar/window icon comes from the `.exe`'s embedded icon (rcedit) — a `BrowserWindow.icon` is **not required** for PKG-04. It only helps the `npm start` dev run and non-Windows. If added, keep it guarded so the dev run (running from `dist/`) still resolves:
```ts
// optional, low-risk addition inside createWindow()
import { app } from 'electron';
const win = new BrowserWindow({
  width: 1024, height: 768,
  icon: join(__dirname, '..', 'build', 'icon.ico'), // dev; packaged exe uses embedded icon
  webPreferences: { /* unchanged */ },
});
```
**Recommendation:** treat this as optional. PKG-04 is satisfied by `win.icon` in the builder config; adding a `BrowserWindow.icon` touches the hardened window for marginal Windows benefit. Planner's call.
